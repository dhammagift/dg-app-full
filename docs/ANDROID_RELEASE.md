# Выкладка Android без ручной загрузки

CI умеет сам отправлять подписанный AAB в Google Play — так же, как iOS-билд уходит в TestFlight.
Джоба `android-release` в `.github/workflows/build-app.yml`.

Пока нет секрета `PLAY_SERVICE_ACCOUNT_JSON`, джоба **ничего не делает и честно пишет об этом**
в сводке рана: зелёная галочка без загрузки — худшее, что может случиться с релизным пайплайном.

## Что настроить один раз (это может сделать только владелец аккаунта)

Сервисный аккаунт целиком делается в Google Cloud; Play Console узнаёт о нём только через
«Пользователи и разрешения». Страницы «Доступ к API» и связывания проекта в консоли искать не
надо — их там нет, и они больше не нужны: *«You no longer need to link your developer account to
a Google Cloud Project in order to access the Google Play Developer API»*
(developers.google.com/android-publisher/getting_started). Инструкции в интернете, которые ведут
в «Setup → API access», описывают консоль позапрошлой версии.

1. **Включить API.** https://console.cloud.google.com/apis/library/androidpublisher.googleapis.com
   → выбрать проект → **Enable**. Подойдёт любой проект (привязки к аккаунту разработчика больше
   нет), но API должен быть включён именно в том, которому будет принадлежать сервисный аккаунт —
   такой порядок в документации.

   **Лучше создать отдельный, например `dg-play-ci`.** Не ради прав — ролей в Cloud этот аккаунт
   не получит вообще и внутри своего проекта не сможет ничего, — а ради порядка: ключ от него
   единственный секрет в GitHub, в своём проекте он изолирован от Firebase, через который работает
   вход на сайте, и перевыпуск ключа не трогает ничего чужого. В чужом проекте сервисный аккаунт
   останется в IAM навсегда, и через год никто не вспомнит, что это. У самого приложения Firebase
   нет: `google-services.json` в репозитории отсутствует, плагин не применяется.
2. **Создать сервисный аккаунт.** https://console.cloud.google.com/iam-admin/serviceaccounts
   → **Create service account** → имя любое (`play-ci`) → **шаг с ролями Cloud пропустить**, права
   выдаются не здесь → создать. Затем открыть аккаунт → вкладка **Keys** → **Add key → Create new
   key → JSON**; файл скачается. Email аккаунта — вида `play-ci@<проект>.iam.gserviceaccount.com`.
3. **Выдать права в Play.**
   https://play.google.com/console/u/3/developers/5361675220359422085/users-and-permissions
   («Пользователи и разрешения»; `5361675220359422085` — id аккаунта разработчика, он же в адресной
   строке консоли, `u/3` — номер гугл-аккаунта в браузере, может отличаться)
   → «Пригласить пользователя» → этот email → в правах приложения выбрать `gift.dhamma.twa` →
   право **«Загружать приложения в тестовые каналы»** (Release apps to testing tracks).
   Больше ничего не давать: этого хватает для внутреннего трека и не хватает, чтобы выкатить
   что-то читателям.
4. **GitHub → Settings → Secrets and variables → Actions → New repository secret**
   → имя `PLAY_SERVICE_ACCOUNT_JSON`, значение — **содержимое JSON-файла целиком**.

Правило Play «первую сборку загрузите вручную» нас не касается: пакет `gift.dhamma.twa` в консоли
уже есть, он заменил листинг TWA.

## Как отправлять

**Руками:** Actions → **Build App** → Run workflow → включить галочку **release**.
**Тегом:** пуш тега — отрабатывает без галочки.

Обычный пуш в ветку и ручной ран без галочки **никуда ничего не отправляют** — ни в Play, ни в
TestFlight. Раньше любой ручной ран уходил в App Store Connect, и это чинилось дважды, с обеих
сторон; правило владельца (20.09.2026): ручной ран не релизит.

## Куда именно приезжает

**Internal track.** Не production, и это осознанно:

- доезжает до устройства за минуты, без ревью;
- видят только тестировщики, перечисленные в консоли;
- на продакшен всё равно нужен **promote** в Play Console — то есть автоматическая загрузка
  физически не может выкатить что-то читателям сама.

Повышение internal → production остаётся ручным решением. Это ровно та часть, которую никто не
просил автоматизировать.

## Что уезжает

Артефакт `dg-app-full-aab-release-<run>` из той же сборки — не пересборка. То есть в Play уезжают
ровно те байты, против которых прогнались проверки и которые лежат в артефактах рана.

`versionCode` = номер рана, `applicationId` = `gift.dhamma.twa`, подпись — релизный ключ из
секретов (`ANDROID_KEYSTORE_*`). Если ключа нет, `build` не соберёт AAB, и загружать будет нечего —
это видно в сводке.

## Соседние репозитории

Владелец (20.09.2026) выдал сервисному аккаунту права на все свои приложения и просил настроить
то же самое для остальных — **после** того, как схема подтвердится здесь. Что есть на деле:

| Репозиторий | `applicationId` | Что сейчас | Что делать |
|---|---|---|---|
| `dg-app-full` | `gift.dhamma.twa` (AAB), `gift.dhamma.mobile` (тестовый APK) | джоба `android-release` | проверяется |
| `notApp` | `gift.dhamma.noapp` | только GitHub-релиз | перенести джобу один в один, поменяв `packageName` |
| `dg-twa` | `gift.dhamma.twa` | только GitHub-релиз | **не настраивать** |

Почему `dg-twa` — «не настраивать»: он объявляет тот же пакет, который теперь шлёт `dg-app-full`
(приложение заменило листинг TWA). Два репозитория, способные залить один пакет в один трек, —
это грабли: чей `versionCode` выиграл, выяснится уже в консоли.

`otrn`, `dictPlugin`, `ddg-ui` Android-приложений не содержат — `applicationId` в них нет.
Если в консоли есть третье приложение, надо сперва выяснить, где оно собирается.

## Если что-то пошло не так

| Сообщение | Причина |
|---|---|
| `Missing repository secret: PLAY_SERVICE_ACCOUNT_JSON` | секрет не задан — см. шаг 4 |
| `The caller does not have permission` | сервисный аккаунт не приглашён в консоль или ему не выдано право на это приложение (шаг 3) |
| `Version code N has already been used` | ран с таким номером уже загружали; следующий ран возьмёт новый номер |
| `APK specifies a version code that has already been used` | то же самое |
