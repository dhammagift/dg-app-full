# Системный поиск: Android AppSearch, iOS Core Spotlight

Задача: отдать лёгкие метаданные библиотеки в поисковые движки ОС и открывать нужный текст по тапу
из системной выдачи. Полные тексты не индексируются — они и так лежат в `dg.db` (612 МБ), а
системный индекс обязан остаться в мегабайтах.

## Что в индексе (уровень 1)

| поле | значение | зачем |
|---|---|---|
| `id` | `sn1.1` (и форма `sn 1.1`) | поиск по номеру |
| `title` | палийское название | поиск по названию |
| `titleFolded` | то же без диакритики | `dhammacakkappavattana` вместо `Dhammacakkappavattana` |
| `category` | `vinaya`, `majjhima`, … | иерархия |
| `snippet` | первая строка | подпись в выдаче |
| `url` | `https://dhamma.gift/<id>` | тап открывает ридер (App Link, `DEEP_LINKS.md`) |

Чего здесь нет и почему:
- **полного текста** — дублировать 612 МБ в системный индекс нельзя, и незачем: настоящий поиск по
  словам уже работает в приложении (`dg.db`, FTS5 `trigram remove_diacritics 1`);
- **ключевых слов на сутту** (уровень 2: `sariputta` находит все сутты с Сарипуттой) — это уже не
  «только метаданные»: +2–4 МБ и шумная выдача. Отдельное решение, если понадобится.

Диакритику системные токенизаторы сворачивают не всегда и по-разному, поэтому свёрнутая форма
кладётся в индекс нами (`titleFolded`), а не ожидается от ОС.

## Android: платформенный AppSearch, без новых зависимостей

`android.app.appsearch` — публичный API с Android 12. `androidx.appsearch-local-storage` **не
берём**: он везёт собственный нативный движок (несколько МБ на ABI), а платформенный уже на
устройстве. Ниже API 31 `available()` отвечает `available:false`, и остаются динамические шорткаты,
которые там уже работают.

`setSchemaTypeDisplayedBySystem("DhammaSutta", true)` — это и есть «доступно глобальному поиску»:
без него тип существует, но ни одна системная поверхность не вправе его показать. Что именно
покажет Samsung Finder или поиск Google — решает потребитель, поэтому проверка на устройстве
обязательна и входит в спайк.

Клик по результату: `id` → `https://dhamma.gift/<id>` → существующий verified App Link →
`_nativeRoute` → ридер. Отдельный системный путь `android.app.search.SearchTarget/SearchAction`
(тап из системной выдачи) помечен `@SystemApi` — обычному приложению он недоступен.

## Два набора: библиотека и история

Библиотека — публичный набор. История и избранное — **отдельный приватный**: если сделать его
публичным, любое приложение прочитает историю пользователя через `GlobalSearchSession`. Разделение —
разные схемы (Android) или разные `domainIdentifier` (iOS). Заголовки блоков в выдаче рисует ОС:
своих подписей «Избранное и история» / «Тексты» приложение нарисовать не может. На iOS идиоматичное
разделение — библиотека через `CSSearchableItem`, история через `NSUserActivity`.

## Когда индексируем

После того как офлайн-слой принял базу (совпал `meta.build_id` с манифестом) и только если
`build_id` отличается от последнего проиндексированного. Батчами: AppSearch кладёт по 200
документов на запрос (лимит binder-транзакции).

## Спайк (Android, 2026-09)

`DgSearchPlugin.SPIKE_SEED` кладёт 6 реальных текстов — этого достаточно, чтобы ответить на один
вопрос: показывает ли наша выдача системный поиск вообще. Порядок проверки:

1. Поставить APK, открыть приложение один раз (сид срабатывает в `load()`).
2. Поиск на телефоне: `Dhammacakkappavatta` или `Mūlapariyāya`.
3. Нашлось → тап открывает ридер; тогда сид удаляем и пишем настоящую индексацию из `dg.db`.
   Не нашлось → Android-половина закрывается шорткатами, а AppSearch остаётся корпусом для
   `GlobalSearchSession` и внутреннего поиска.

Методы плагина: `available()`, `index({items})`, `query({q, limit})`, `clear()`. `query` доказывает
индекс изнутри приложения, без участия лаунчера.
